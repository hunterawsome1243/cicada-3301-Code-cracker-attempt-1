The Phase 3 beam kernel is built (`runeforge/gpu/beam_kernel.py`, numba.cuda, one thread per key; `tests/test_gpu_beam.py`). One Python function is compiled both as the CUDA device function and as a CPU njit twin. The twin matches `beam.decode_batch` exactly (max |Δscore| = 0 on 10⁴ keys per decoder, and on the template lane's own keystreams: `python -m runeforge.gpu.parity lanes/_template.yaml --backend cpu-twin`). The kernel matches on numba's CUDA simulator, and its PTX compiles for sm_75/86/89. It has never run on a real GPU. `runeforge sweep --backend gpu` (beam lanes only) is wired: keys come from the CPU generator, the kernel scores them, and survivors, crossers and chunk bests are re-decoded on the CPU reference (a disagreement over 1e-6 stops the sweep). It refuses a lane without a passing real-device `runs/<id>/parity.json` bound to the lane spec, `beam.py`, the kernels and the device.

The `mt19937-py27` keystream kernel is built the same way (`runeforge/gpu/mt_kernel.py`; `tests/test_gpu_mt.py`): CPython 2.7's `random.seed(<int>)`, `genrand_int32` and the four reducers in one function, one thread per seed, rows left on the device for the beam kernel. Its twin equals `generators.keystream_batch` symbol for symbol in every mode, for 32- and 64-bit seeds, with offsets and over 13,000-symbol streams (about 40 twists); the CUDA kernel equals it on the simulator and its PTX compiles for sm_75/86/89. The parity record now carries a `keygen` section (the lane's window on every seed, the crosser record budget on 64), and `sweep --backend gpu` generates this family's keys on the device (`status.json` `keys_backend`).

## Lessons

- 2026-10-22, instrument (FOUND-ERROR, own toolbox): `interrupt_prob` defaulted to 0.44, reading "WELCOME 11 of 25" as P(a plaintext F is an interrupter). It counts ciphertext ᚠ's; every plaintext F in the keyed solved sections is an interrupter (14/14). Default corrected to 1.0 (`runeforge/lanes.py`); frozen docstrings carry the same misreading (TR-4). Consequence, measured: under the every-F rule the template lane's family fails the gate on C1 in 12/12 keys (`python scripts/beam_power.py`, gate section). LP2 0-55 holds 458 ᚠ against 446.8 for uniform runes, where English-register plaintext with every F unencrypted would put ~650-780. So under the every-F rule (1.0) the family fails C1 on 12/12 keys; `interrupt_prob: 0.0` passes cleanly and 0.1 and 0.44 pass marginally (C3 on 2 and 3 of 12; `reports/beam_decoder.md` §3); the template lane uses 0.0; the earlier "GATE PASS, marginal C3" below was measured at the misread 0.44.
- 2026-10-22, instrument: the spec's "rigid screen, beam on survivors" cannot see a filtered key -- a rigid decode of a planted anti-repeat key scores like noise (control 0/20), so it never reaches the survivors. Rule 2 (the control runs the sweep's own pipeline) puts the beam in the screen itself: a `:beam*` lane decodes every key with the beam in its control, nulls and sweep. CPU cost ~1,000-2,500 keys/s at L = 240 (beam ~2,500, beam-skip ~1,240, beam-skip-int ~1,000) against about 10^5 rigid (`reports/beam_decoder.md` §6, noise).
- 2026-10-22, calibration: a beam lifts wrong-key noise above uniform strings (it picks the best interrupt/skip path through the wrong key): at L = 240 with lp-ngram3-heldout the wrong-key mean is -6.90 (beam), -6.87 (beam-skip), -6.74 (beam-skip-int) against -7.17 rigid (`scripts/beam_power.py` noise). Beam bars therefore come from beam nulls (`runeforge/scoring/beam_calib.py`), never from the rigid calibrations.
- 2026-10-22, calibration (adversarial review): an interrupt decoder's wrong-key null rises with the window's canonical F count (`beam`, L = 240: block-max mean -6.57 at 4 F's, -6.32 at 20, `scripts/beam_power.py` fcount; `beam-skip` flat), so a bar fitted on fresh uniform ciphers sits below an F-rich window's own null. `beam` / `beam-skip-int` bars are fitted at the most F's of any LP2 page-start window (L = 120: 10, page 43; L = 240: 14, page 11) and a lane whose window holds more is not runnable. The first-round fits (uniform ciphers, max_skip 2) were withdrawn before anyone installed them.
- 2026-10-22, instrument: under the rigid decoder no lane can pass both the fingerprint gate and its planted control. LP2's doublet deficit (86 vs 447 expected) is reproduced only with the anti-repeat filter (`runeforge gate lanes/_template.yaml`: GATE PASS, marginal C3 C6 [2026-10-22, re-measured: GATE PASS, marginal C3 on 3 of 12 keys at the then interrupt_prob 0.44; C6 does not reproduce; `scripts/beam_power.py` gate]); without it the doublet rate is ~5x LP2's and the gate excludes the family. But the rigid decoder cannot follow the filter's key skips, so the control of every filtered lane is `INCONCLUSIVE (power)` (`runeforge control lanes/_template.yaml`: recovered 0/20). Every lane today therefore ends `EXCLUDED (gate)` or `INCONCLUSIVE (power)`; the Phase 2 beam decoder is the critical path, not more sweeping. [2026-10-22, later: this holds for rigid-decoder lanes only. The template now runs `lp-ngram3-heldout:beam-skip` at `interrupt_prob: 0.0`, and the same control identifies 20/20 (gap 1.160 nats with the per-plant β, 1.114 with the staged β; `scripts/beam_power.py` template_control).]
- 2026-10-22, instrument: the oracle cannot tell a one-time pad from a key (k = c - p maps any page to English and passes, `tests/test_oracle_cli.py`). A key's provenance -- generator, seed, and the bar at the lane's true N -- is what HIT_PROTOCOL.md steps 4-5 check; `--key-module` must be the generator's own keystream (`--lane` decodes it the lane's way).
- 2026-10-22, calibration: the Gumbel extrapolation from block maxima errs conservative -- the single max of 10^6 null draws fell below the predicted mean max in all 8 fits (`runeforge/scoring/calib/presets/*.json`, `check`), so bars at 2^32 are slightly high (fewer false positives, slightly less power). [2026-10-22, later: this holds for the 8 rigid fits only. In the 6 beam fits the 10^6 max is above prediction in 3 (up to +1.4 beta, beam-skip-int L = 240): treat beam bars as good to about 1.5 beta, `reports/beam_decoder.md` §4.]
